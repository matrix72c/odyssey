# Odyssey 功能设计

## 1 目标与范围

### 1.1 产品目标

1. 让长任务在模型请求中断、权重更新和 GPU 角色变化时保留可接续进度。
2. 按算法要求组织训练数据，利用超发、动态过滤和慢组延后维持训练供给。
3. 用一个逻辑统一的调度器协调任务供给、训练推进、权重发布与 T/P/D 资源，避免各阶段独立扩缩容相互争抢。
4. 支持可靠的模型与数据恢复、资源核对和清理，能够运行真实长任务及 GLM-5.3 规模训练。
5. 保持模块职责清晰；更换算法、任务、后端或调度策略时，通过对应边界扩展。

研究主线：在有界异步约束下联合调度训练数据供给与 T/P/D 资源，计入版本风险和状态转换成本。最接近的已有工作是 [QwenGyre](https://arxiv.org/abs/2609.33848)（rollout 与训练之间的弹性 GPU 切换），本项目的贡献须落在它未覆盖的部分。候选机制、研究门槛和对照计划见[实施计划](Plan.md)，它们不是框架交付要求。

### 1.2 必须覆盖的运行模式

| 模式 | 必须具备的能力 | 使用条件 |
| --- | --- | --- |
| 完整任务 GRPO | 组统计、异步候选池、超发、过滤补采、跨 batch 延后 | 每组规定成员均取得有效评估；版本与任务混合合规 |
| 完整任务 PPO | 独立 actor/critic、value/GAE/returns、多 epoch、完整恢复 | `ppo_v1`，`async.mode=sync` 或 `bounded` |
| 有界异步训练 | 混合行为版本记录、drop/wait、受控发布 | GRPO 与 PPO 均支持；同步是 `max_age=0` 的特例 |
| 请求与任务接续 | 请求接续、任务暂停/继续、保留累计预算 | 所有模式必须支持；不依赖中间奖励 |
| 静态 PD | 独立 P、D 计算组，完整推理状态交接，P 侧前缀缓存 | 目标模型、状态格式、布局与网络组合已通过实际验收 |
| T/P/D 弹性 | 有限合法布局间的边界重构，成功后继续训练和服务 | 在后端声明的安全点执行；不在任意 collective 中途改成员 |

调度策略只提供 `fixed` 与 `joint` 两种，共用同一约束校验。

### 1.3 不要求的能力

多租户或跨作业调度、外层平台自动扩缩容、任意 TP/EP/PP 在线重分片、optimizer 更新中途加入成员、开放 batch 的未知分母训练、通用参数服务器、通用工作流引擎、任意外部工具副作用回滚、partial learning（中间评估 GRPO 与分段 PPO）、作业内评测副本、数据库主节点切换。

每个合法稳态布局保留非零 T 容量和非零训练请求服务容量；T 的规模及 GPU 成员可以变化，但不交付把训练或推理角色缩到零后再恢复的模式。独立 rollout/eval 命令不创建 T 组。

## 2 实施与复用边界

Odyssey 是独立项目，仓库、Python 包和 CLI 均命名为 `odyssey`，代码位于 `src/odyssey/`。`../sandbox_rl/` 及其运行环境保持只读：所需模块复制或提取到 Odyssey，在提取处注明来源与许可证，并独立验收；不得导入 `sandbox_rl`、链接旧源码或共用旧虚拟环境。可参考 [sandbox_rl 代码地图](../../sandbox_rl/docs/Code_Map.md)、[训练指南](../../sandbox_rl/docs/Training_Guide.md)和 [PPO 构造](../../sandbox_rl/src/sandbox_rl/config/training/_ppo.py)。

XTuner、LMDeploy、Lagent 以 fork 的 integration tag 接入，与 sandbox_rl 共用同一套 `-run` worktree，规则见父工作区 AGENTS.md；可复用入口与后端事实见[复用清单](Reuse_Map.md)。

参考实现的 RLOO、PPO smoke 和 live partial 仅作迁移对照：RLOO 不等于本项目 GRPO，同 owner 接续不证明 owner 重启恢复，小模型结果不替代目标规模验收。Odyssey 不解析或导入 sandbox_rl 的历史 run；需要比较时编写等价配置重新运行。

## 3 业务对象与共同规则

### 3.1 基本对象

recipe 是一套明确的算法与数据使用规则；actor 是生成动作的策略模型，critic 是 PPO 的价值模型。任务执行、训练数据使用和资源分配是三个独立生命周期。

| 对象 | 含义 |
| --- | --- |
| Task | 原生任务、环境和评估规则，沿用 Harbor 任务事实 |
| Group | 同一采样问题下一起比较的固定成员执行集合；是准入、组批和退役的单位 |
| Execution | 一次逻辑执行，可包含多轮请求、工具、子 Agent 和多个沙盒 |
| Attempt | 一次执行尝试；重试有新 attempt，但不自动成为独立样本 |
| Request | 一次逻辑模型调用；换引擎和重试不改变身份。记录父请求与复用前缀长度，同一 execution 的请求构成请求树 |
| Assessment | 对执行终态的评估，包含有效性、分数及信用分配范围 |
| BatchManifest | 一次选定的不可变训练输入清单：group 成员、来源配额和使用次数 |
| TrainTransaction | 使用一个冻结批次完成一组训练阶段；可以包含多个实际 optimizer update |
| ModelVersion | actor 或 critic 的参数身份，与路由代次和发布次数分开 |
| Publication | 一份 actor 参数被服务端确认安装并可路由的发布事件 |
| ResourceGroup | 一组授权资源及其计算角色、并行布局和成员代次 |

### 3.2 不变量

| 编号 | 规则 |
| --- | --- |
| INV-01 | 任务执行、数据使用、GPU 角色分别有生命周期；任一生命周期变化不能隐式结束另两个。 |
| INV-02 | group 准入时不绑定训练 batch；训练前原子预留并冻结 manifest。目标、mask、权重与归一化在对应反向前固定。 |
| INV-03 | 实际生成 token、上下文、行为概率、行为版本和专家记录不可被重算结果覆盖。 |
| INV-04 | 任务得分、评估有效性、数据合法性、资源清理状态分别记录；基础设施错误不是有效零奖励。 |
| INV-05 | 未关闭 group 上限、执行并发、目标 batch 大小分别配置和核算。 |
| INV-06 | 每个 group 的训练使用有记录；PPO 的 epoch 复用与重复事件分别处理，不重复贡献。 |
| INV-07 | 实际 optimizer 应用才推进对应模型版本；critic 更新不推进 actor 版本；发布另行确认。 |
| INV-08 | 同一 GPU 的活动计算所有权唯一；host offload 和转换峰值也计入资源预算。 |
| INV-09 | 超时不等于操作未发生；结果未知时先查询或恢复，不盲目重发更新与工具操作。 |
| INV-10 | 算法、模型、数据混合、使用次数和版本约束不能被调度器为提高吞吐而静默修改。 |

### 3.3 长任务的时间与准入

同一 execution 的墙钟、生成 token、工具成本、沙盒数和重试预算累计计算，pause/resume 不清零。到期后执行以截断结束，评估时间单独受限。

未关闭 group 数 H 覆盖未启动、运行、暂停、就绪和已预留状态，始终满足 `H ≤ Q`。新 group 只在 `H < Q` 且不存在尚未发布的 actor 更新时准入，因此新 group 总是从最新发布版本开始生成；现有候选已凑不齐下一批时提前发布，避免这条规则造成死锁。group 在全部成员终结、训练使用结清或显式退役后关闭；单次消费或 PPO epoch 不关闭 group。失败退役由 run 级失败预算约束（连续失败数、失败 group 总数、成本与 deadline），耗尽时以确定原因停止。

无限期保留慢任务、严格限制版本年龄、训练始终不等待，三者不能同时保证。年龄按 execution 内最旧的行为版本计算；长任务默认使用 `drop` 加按任务时长和更新速率事前登记的 `max_age`。`wait` 可显式选用，但须通过期限与可行性检查。固定成员、来源配额和 `wait` 可能让训练等待慢任务，这是有意保留的正确性约束；每次运行报告训练空闲比例和原因拆分（FR-12）。

## 4 功能规格

### FR-01 长程多 Agent 与多沙盒执行

支持大量独立任务，也支持单任务内的父子 Agent、多个沙盒、分支与汇合。任务拥有稳定身份，记录每个模型请求、工具调用、父子关系和结果来源。执行器按 harness 能力记录黑盒子 Agent，不强制所有 harness 使用同一编排库。

GPU worker 退出不得销毁独立任务 owner、工作区或仍可继续的工具进程。子 Agent 扇出有并发与总量限制；父任务终止时按任务策略结束子任务并核对所属资源。

真实主线优先覆盖 Claude Code，再覆盖一个具有显式父子任务和多沙盒的实现。其余 harness 列出能力矩阵，不宣称全部支持跨 owner 恢复。

验收：AC-01、AC-02、AC-04、AC-19。

### FR-02 采样、超发与预热

配置 `B`（批次 group 数）、`N`（每 group 执行数）、`Q`（未关闭 group 上限）和 `C`（执行并发）。冷启动按 Q 预热，稳态按第 3.3 节准入，收尾停止新增任务。数据源按固定种子和声明的任务混合产生任务引用。

数据源适配由 Execution 提供；Control 唯一拥有采样游标、随机状态、来源配额和准入决定。C 约束顶层 execution 的活跃执行；暂停保留的 owner/沙盒及子 Agent 另受总量和并发上限约束，不能通过暂停或派生子任务绕过资源预算。

不能默认选择组内最快 N 个，也不能在某个 batch 满后销毁多余候选。准入只获得候选身份，启动还需 CPU、沙盒和推理容量。

验收：AC-03、AC-06、AC-07。

### FR-03 请求与任务接续

请求中断后保留已提交 token、概率、版本、专家记录、停止状态及剩余预算。接续只追加后续输出：在兼容后端迁移状态，或用已提交 token 重算前缀。旧 token 的行为概率、版本与专家记录不变。

任务暂停保留 harness、工具结果、子 Agent、环境引用和预算。不可中断工具运行到安全点，再暂停下一次模型调用；操作返回实际到达的安全点，发出取消命令不代表暂停完成。

分别声明同 owner 接续、GPU worker 重启后接续、owner 崩溃后恢复能力。token 日志不等于任意 CLI 内存和沙盒快照。

验收：AC-04、AC-05、AC-18、AC-19。

### FR-04 评估、动态过滤与有界补采

Assessment 绑定执行终态，记录 evaluator 版本、有效性和分数；对仍在运行的工作区评估必须隔离或暂停写入。

有效零奖励正常参与算法；零方差组是否过滤由 recipe 决定；基础设施失败、评估缺失、轨迹不完整和陈旧度失效使用不同原因码。一个 group 同时命中多个退役原因只退役一次。退役后按第 3.3 节的准入规则补入新 group，受 run 级失败预算约束；不得自动缩小 B 或放宽任务混合。清理失败的数据须隔离，不进入训练。

验收：AC-06、AC-07、AC-20。

### FR-05 异步候选池与动态组批

完成与消费顺序解耦。group 满足完整性、评估有效性、版本限制、任务混合和剩余使用次数后才可参与组批。例如 B=4、A/B/C/E 就绪、D/F 未完成时选择 A/B/C/E，D/F 后续继续参与；不为填满 batch 删除组内慢成员。

批次选择、预留和 manifest 创建在 Experience 内原子完成；事务开始后不可替换成员，重新读取返回同一数据。选择规则至少包含来源配额和合格候选的等待顺序，并记录实际消费分布。

验收：AC-08、AC-09。

### FR-06 GRPO 与 PPO

提供两个 recipe：`grpo_v1` 与 `ppo_v1`（`async.mode=sync|bounded`）。actor 目标统一为裁剪比值以训练侧重算的近端策略为分母、真实行为概率经截断重要性校正进入目标。

GRPO 使用组相对 advantage（组内均值与标准差，沿用 XTuner 的计算），loss 按全局有效 token 数归一化；不能将 RLOO 换名交付。PPO 使用独立 actor/critic 参数、optimizer、scheduler 和版本，支持 value、GAE、returns、value loss、多 epoch 和固定的近端策略快照。returns 由原始 GAE 加旧 value 得到，actor 使用标准化后的优势，二者分别保存。批次目标在各 epoch 之间固定；实际更新次数与批次次数分别记录。真实终止与预算截断的 bootstrap 不同。

默认 actor 与 critic 常驻同一 T 组的 HBM；T 组较小时可配置 host offload 分时。模型身份、快照和更新账本不假设两模型永久同组。

MoE 训练必须启用 rollout router replay：记录 rollout 时各位置、各 MoE 层实际选择的专家，并在 actor 训练前向中回放；训练侧复用 XTuner 已有实现。recipe 保留显式开关用于对照。实现参考模型的 MTP 能力，critic 不使用 MTP。reference KL、entropy、reward shaping 等附加项须显式进入 recipe。

两侧后端只提供所有 logits 处理之前的原始 logprob，因此训练 rollout 不能启用任何改变采样分布的变换：最终引擎配置必须是随机采样、温度 1、无 top-p/top-k/min-p 截断、无重复惩罚、无禁词与约束解码、不忽略 EOS、无最小生成长度；其他配置拒收。停止条件属于采样之后，可以保留。独立评测不受此限制，记录实际采样参数。逐批报告概率比值及裁剪情况；同参数训推偏差由配对探针测量，与异步版本差异分开报告。

验收：AC-11、AC-12、AC-13、AC-15、AC-18、AC-30。

### FR-07 轨迹来源与数据组织

保存真实请求的输入/输出 token、模板与 tokenizer 身份、行为 logprob、实际采样参数、版本 span、父子关系、上下文压缩来源，以及专家记录。工具/用户/观察 token 作上下文，没有训练目标，但其前向所需的专家记录不能省略。

Serving 按渲染后的 prompt 匹配同一 execution 已有请求，命中部分直接复用实际 token，只对新增部分编码；因此请求天然构成请求树，每条根到叶的路径是一条训练序列，共享祖先的目标只贡献一次。模板改写历史、删除思考内容、压缩或截断表现为新分支，不重新分词拼接。默认只在行为版本相同且前缀专家记录一致时合并，否则新开一条计算序列，保证每个训练动作回放产生它的那次前向；跨版本也合并的近似模式只作对照。压缩造成的多条计算序列不切断同一 episode 的动作时序。前缀命中的 token 占比作为合并率上报。

输出在请求结束及暂停、发布、重构、排空等边界持久提交，harness 只看到已提交输出；轨迹通知可重复投递、可补读。大 payload 存入 ArtifactStore（GPFS 或对象存储）并直接读取，控制器不收集完整 token 数组、logits、权重或 KV。

验收：AC-05、AC-10、AC-23。

### FR-08 异步版本与权重发布

分别记录准入版本、实际行为版本、当前 actor、近端策略、critic 快照和服务路由代次；任务跨版本接续时逐 span 记录行为来源。陈旧度按真实 actor optimizer 更新次数计量。

支持 drop 与 wait。wait 在越界前限制 actor optimizer 更新推进，仅停止发布不足以限制年龄。硬期限、不可恢复失败或 drop 触发显式退役。

权重发布须取得一致快照，等待目标服务组安装、核对和路由激活；训练完成不等于发布成功。发布节奏 `publication.every_transactions` 表示最多多少个训练事务发布一次；现有候选已无法组成下一批时提前发布。调度器只能在 recipe 允许范围内选择时机。

验收：AC-14、AC-15、AC-16。

### FR-09 PD 分离

P 和 D 使用独立计算组、容量和并行布局，可单独观察和调整。每次 P→D 交接核对模型身份、完整推理状态、布局和发布版本。

状态包括 KV、线性注意力及其他模型状态；功能验收模型 qwen3_5_moe 的交接必须包含线性注意力状态。P 侧必须支持前缀缓存，否则多轮长任务每轮重新 prefill 全部上下文。跨版本接续重算前缀，不拿旧权重 KV 配新权重。P/D 拥塞、容量不足和交接失败须有背压与恢复路径。

验收：AC-16、AC-17、AC-22。

### FR-10 统一调度与边界弹性

一处作业级决策联合控制任务启动/接续、组批、训练推进、发布和 T/P/D 配置。P/D 不另起抢占资源的 autoscaler；引擎本地 batching 和训练内部并行由后端管理。

首版在有限合法布局和转换中选择，依据合格数据供给、P/D 负载、版本压力、工具状态、状态位置与切换成本；包含保守收益门槛、最短驻留、未知观测处置和固定布局回退。调度计入训练通信、权重发布、P→D 传输和 checkpoint 的共享网络竞争，控制大规模搬运的启动时机与并发；不逐算子或逐请求批准通信。

训练侧在事务边界重建组，每个成员退出旧组、加入新组并恢复模型和 optimizer；Serving 在请求安全点交接或暂停。重构期间计入新旧状态和通信峰值。

验收：AC-17、AC-21、AC-22、AC-23、AC-24、AC-26。

### FR-11 恢复、停止与资源清理

共同 checkpoint 关联 actor/critic、optimizer、scheduler、RNG、训练事务、数据预留/消费、准入账本、recipe、版本和配置。checkpoint/restore 是各有状态模块的显式接口；Control 负责共同恢复边界。批次预留绑定唯一事务；只有确认该事务不会迟到执行且没有已应用更新，才可释放预留。

恢复按影响面分三级：

- R0：仅控制进程退出。同节点 supervisor 重启 Controller，接管仍存活的长期 worker，不回滚模型。
- R1：存活节点上单个进程级故障（推理实例、execution owner 等）在域内重建，其他域继续。
- R2：训练状态丢失、更新结果无法判定或节点故障。由平台自愈重启作业，从最近已提交的共同 checkpoint 恢复。

结果未知的参数更新先对账，无法判断时走 R2。R2 后未关闭的 group 只要有成员依赖已消失分支的行为，整组退役，不能替换或删去该成员继续使用原组；保留事实日志与产物，停止并清理所属 execution，按失败预算补入新 group。首版不提供“退出训练但继续跑完”的模式。

恢复账本与关键元数据存于集群部署的 PostgreSQL。写入检查与记录提交是同一事务；所有已返回成功的记录都能恢复；提交结果未知时按操作 ID 查询，不当作失败重做；数据库不可用时暂停依赖持久提交的推进。数据库事务不代替工具、optimizer 或 GPU 进程的实际结果核对。

支持停止新增、限时排空、强制停止与最终对账。清理覆盖模型请求、工具/子进程、沙盒及租约、路由、Ray actor/placement group 和作业拥有的 GPU 占用；仍有残留时返回非成功状态及可定位清单。

验收：AC-18、AC-19、AC-20、AC-21。

### FR-12 评测、观测与复现

评测在训练作业之外进行：训练按配置周期把已成功发布的 actor 版本导出为 HF 权重，目录以 run_id 和版本命名，写入后不修改，保留到显式删除；`odyssey eval` 读取该目录，自行启动推理与执行，按固定任务集、种子和预算评测。评测不继承训练的过滤与补采，报告有效零分、未评分、基础设施失败和清理异常，以及实际采样参数。训练不等待评测；导出成本计入训练报告。

每次调度记录输入观测、候选方案、拒绝原因、所选动作、成本估计和实际结果。记录从准入、请求、评估、batch 到参数更新和发布的关联身份。

运行产物包含不可变配置、代码 git rev 与 uv.lock、模型身份、任务与镜像版本、能力报告、资源预测记录、训练指标、checkpoint 和清理报告；凭据不写入快照和日志。

每次运行报告 `training_idle_ratio` 及原因拆分。窗口从首个 T 组 READY 到最终停止开始，包含采样预热；prepare 辅助前向及 actor/critic 计算计为忙碌，其余为空闲。每段空闲有一个主因（至少区分等组完成、陈旧度 wait、来源配额、等待发布、资源转换，另列 checkpoint、恢复、其他、未知），主因时长之和等于空闲时长，未知不记为零。

性能记录关联后端执行配置、并行布局、硬件/网络、工作负载和测量窗口，区分 actor/critic、P/D、发布与 checkpoint；聚合指标常态采集，细粒度 trace 按窗口采样。

验收：AC-25、AC-26、AC-27。

### FR-13 目标规模与运行效率

目标为 GLM-5.3（含 MTP 层约 753B 总参数、约 40B 激活）actor 加同规模 PPO critic，在约千卡 H200 集群（每节点 8 卡、1.8 TB 内存）上训练。功能验收模型为 qwen3_5_moe。实际节点数、布局和权重路径由运行配置固定并记录。

容量按第 8.6 节核算：两模型训练状态约 21~24 TB，T 组不少于约 384 卡时可同时常驻 HBM；推理默认 FP8，每副本约 0.76 TB、单节点可容纳；共同 checkpoint 约 18 TB，经主机内存暂存后异步写入存储。

衡量同质量训练耗时、GPU 小时、有效训练进度、任务/数据等待、超发浪费、前缀重算、切换和恢复开销；新数据产出与 PPO 重复 epoch、原始 token 吞吐分别统计。

通算机制归属：训练内部通算融合和 MoE dispatch/combine 由 XTuner 实现，推理内部优化和 P→D 传输由 LMDeploy 实现，本项目对应负责人负责配置、集成、测量和后端缺口；跨 T/P/D 的搬运、发布和网络竞争由 Control 协调。调整执行配置必须保持有效 batch、样本贡献、mask/归一化、PPO epoch 和 optimizer 更新语义。

小模型用于实现与故障检查；目标规模独立验收。模型或资源未提供时标记受阻，不能以缩小模型、去掉 critic 或只跑推理替代。

验收：AC-23、AC-26、AC-28。

### FR-14 可维护性与扩展

六个业务模块与薄基础设施层边界明确：算法不操作 Ray，Execution 不导入训练后端，公共控制协议不传后端对象；数据、训练与服务拥有各自真实状态，Control 保存命令和观测投影。

通用能力优先复用成熟组件，通过薄适配层接入；自研集中在 RL 业务规则、数据合法性和调度策略。元数据用 PostgreSQL，大文件用 ArtifactStore（GPFS 与 Petrel 对象存储两个后端），诊断日志用标准 logging。

`fixed` 与 `joint` 策略统一经过同一约束校验；新增策略不修改 reward、数据使用或底层计算机制。扩展点只服务实际的任务、算法、后端和策略，不建设通用插件平台。

验收：AC-24、AC-27、AC-29。

## 5 配置与使用流程

### 5.1 配置内容

在 Odyssey 内实现 experiment/config groups → 不可变 run 快照的链路，字段用严格类型校验，未知字段报错。

| 配置域 | 必填或显式选择的内容 |
| --- | --- |
| task | 数据源、训练/评测划分、harness、沙盒/子 Agent 限额、时间/token/工具预算、恢复能力 |
| recipe | `grpo_v1` 或 `ppo_v1`、组大小、裁剪与校正参数、actor/critic 更新次数、routing replay 开关、附加项 |
| sampling | B/N/Q/C、来源配额、过滤、失败预算 |
| async | `max_age`、drop/wait、发布间隔；PPO 的 `async.mode` |
| evaluation | 导出周期、导出位置；独立评测的任务集、种子、预算与采样参数 |
| backend_profiles | 后端执行配置、适用模型/布局与生效安全点 |
| resources | 外层资源池、非零 T/服务布局、合法转换、内存和网络预算、大规模搬运并发 |
| scheduler | `fixed` 或 `joint`、观测失效时限、最短驻留、收益门槛、固定回退布局 |
| reliability | 操作 deadline、checkpoint 周期、重试上限、停止和清理 deadline |
| persistence | PostgreSQL 连接（地址与凭据来自环境）、ArtifactStore 后端与位置 |

学习提升阈值、健康阈值、统计方法和预算在对应验收开跑前登记，见[实施计划](Plan.md)。缺少所选功能所需的字段、后端能力或任务条件时启动前报错，不静默关闭 critic、PD 或恢复 optimizer。

### 5.2 标准使用路径

1. 选择任务、模型、recipe、资源配置和调度策略，生成不可变 run。
2. 离线校验模型/布局组合与预算；按授权分区完成实际资源形状预测。
3. 启动作业，建立固定初始布局，安装初始服务权重并预热候选任务。
4. 持续执行、评分和组批，按 recipe 训练与发布；控制器逐步启用允许的弹性。
5. 周期保存共同 checkpoint、导出评测权重并记录指标。
6. 到目标或收到停止命令后排空/终止，完成数据处置和资源核对。

状态输出能区分等待数据、准入、模型服务、训练、发布、重构和清理。

## 6 验收场景

AC 的通过条件只在本表定义。结果分为 PASS、FAIL、BLOCKED、NOT_RUN，后两者不等于通过；各 AC 的状态与证据位置记录在[实施计划](Plan.md)。涉及学习提升的 AC 须在开跑前登记任务划分、种子、更新数、预算、阈值与统计方法，不得看过结果后调低。

| 编号 | 场景与通过条件 | 最低证据层级 |
| --- | --- | --- |
| AC-01 | 并发独立任务完成；请求、工具、评分与清理可关联，任务身份不混淆 | CPU 契约 + 真实任务 |
| AC-02 | 一个父任务派生至少两个子 Agent，跨至少两个沙盒，汇合结果；父任务退出后资源可核对 | 真实任务 |
| AC-03 | Q 大于 B，C 小于候选总执行数；任何时刻未关闭组、活跃执行和沙盒均不越各自预算 | CPU 状态机 + 运行日志 |
| AC-04 | 工具等待和模型请求期间分别暂停；恢复保留环境/请求身份、旧结果与累计预算，不重复工具调用 | 真实 Agent 与后端 |
| AC-05 | 生成中断后按 cursor 接续，跨版本重算前缀；无 token 重复/缺失，旧 logprob/版本/专家记录未改写；通知丢失后补读已提交记录 | 真实推理后端 |
| AC-06 | 同组同时命中过滤、失败和过期，只退役一次；有效 0 分不变成失败 | CPU 契约 |
| AC-07 | 持续失败、全被过滤、发布失败、暂停任务耗尽预算时有确定的等待/补入/停止路径，失败预算耗尽即停止；K>1 时候选按来源配额凑不齐下一批即提前发布 | 故障注入 |
| AC-08 | A/B/C/E 先就绪即组批；D/F 后续消费，已完成兄弟结果保留，组内慢成员不被删除 | CPU + 端到端 |
| AC-09 | 并发预留同一 group 时只有一个成功；预留绑定唯一事务，重复提交不重复使用；释放后迟到 execute 被拒，未知/已应用更新不得释放 | CPU + 故障注入 |
| AC-10 | 请求树、压缩分支和共享前缀的来源正确，共享祖先只贡献一次；packing 不改变语义。`exact` 模式下，每个训练动作的完整上下文（输入前缀与生成位置）回放产生它的那次 rollout 前向的专家记录，覆盖跨版本接续、缓存未命中和并行切分，概率和梯度与相同专家选择的参考计算相符；`approximate` 模式另报告前缀不一致率，并与 `exact` 在同参数、同输入下对照 logprob、loss、梯度 | 数据契约 + 真实 MoE 后端与 GPU |
| AC-11 | GRPO 与独立小样本参考计算一致：奖励、mask、token 级分母和梯度核对，证明不是 RLOO；同参数时比值为 1，陈旧数据的校正按 c_max 截断 | CPU 数学 + GPU |
| AC-12 | PPO actor/critic 均有实际更新；GAE/returns 固定，多 epoch 使用有记录，各自 scheduler 和版本正确 | GPU 至少两次 actor 更新 |
| AC-13 | `async.mode=sync` 与 `bounded` 严格区分；行为/近端/critic 快照可查；终止与截断的 bootstrap 数值符合规则；压缩后跨多条计算序列的 episode 的 GAE 与单序列参考计算一致 | CPU 数学 + GPU |
| AC-14 | 同步配置（`max_age=0、Q=B`）能持续推进；wait 在下一次 actor 更新会使事务外 group 越界前阻止推进；停发布但继续更新不能绕过；manifest 版本与 prepare 快照不一致时重新预留；到硬期限后可处置解阻 | 状态机 + GPU |
| AC-15 | optimizer SKIPPED 不增版本；critic 更新不增 actor 版本；更新回执丢失不造成重复 optimizer step；部分 rank 应用不能报告全组 APPLIED | 故障注入 + GPU |
| AC-16 | P/D 错误版本或不兼容状态被拒；正确组合生成；P/D 专家记录完整可回放；P 侧前缀缓存命中且发布后不复用旧缓存；安装部分失败不激活错误路由 | 真实 PD + 故障注入 |
| AC-17 | P 或 D 扩缩后继续服务；GPU 转为 T 后完成真实更新，再转回推理；任务 owner 存活 | 多节点真实后端 |
| AC-18 | 新作业从共同 checkpoint 恢复 actor/critic/optimizer/scheduler/RNG 与数据使用进度，模型与使用账本对应同一时点，Experience 从 checkpoint 记录的消费游标补读；R2 后受影响 group 整组退役并在失败预算内补入；不能只加载 HF 权重 | GPU 恢复对照 |
| AC-19 | 分别杀推理实例、execution owner 和 Controller；前两者按 R1 恢复或显式失败、不虚假复活，Controller 按 R0 接管且不回滚模型 | 真实故障注入 |
| AC-20 | 正常完成、超时和强制停止均产生清理清单；注入清理失败时报告残留，不 exit 0 | 独立资源查询 |
| AC-21 | 重构失败、旧进程迟到、Controller 重启时拒绝旧 run_epoch 的操作；真实 PostgreSQL 上已确认记录在回执丢失和数据库重启后可恢复；不双重占用资源、不双重更新 | 数据库恢复检查 + 多节点故障注入 |
| AC-22 | 功能验收模型（按 model_type 与权重路径标识）完成完整推理状态交接及至少两种训练规模间的重构；不支持组合在准备阶段拒绝 | 真实后端 |
| AC-23 | 控制面只传摘要/引用，CPU、GPU、存储和转换峰值受预算控制。GRPO + 有界异步 + PD 下，一个实际持续两小时以上的任务依次经历跨版本发布、一次资源转换和一次 R1（优先推理实例丢失后按 cursor 接续），同次运行另注入一次 R0；任务最终完成、合法数据参与真实更新，清理可独立核对 | 真实长任务联合验收 |
| AC-24 | `fixed` 与 `joint` 共用算法约束；`joint` 与扫描配比后最优的 `fixed` 在相同 recipe、任务混合和资源预算下对照；无收益或观测失效时保持/回退合法配置 | 策略测试 + 对照运行 |
| AC-25 | 训练继续更新和发布期间，导出的版本可被 `odyssey eval` 读取并评测；评测不应用训练过滤补采，报告实际采样参数、完整分母、失败与未评分；导出目录在训练后续发布和退出后仍可读 | 真实训练 + 独立评测 |
| AC-26 | 相同 recipe、数据混合和预算下记录有效进度、质量、GPU 时及转换成本；每次运行的空闲比例与主因拆分可由时间线复算；训练与 PD 服务各有不受其他角色流量干扰的基线，并实测与发布、状态传输、checkpoint 并发时的干扰；后端配置变更核对数值语义；未测组合标为未知，无未经测量的加速结论 | 真实后端测量 + 可复现报告 |
| AC-27 | 新进程能根据 run 配置、代码 git rev 与 uv.lock 重建运行；无凭据泄漏；未知字段与不支持组合明确失败 | 配置契约 |
| AC-28 | GLM-5.3 actor + 同规模 critic 在约千卡上完成训练、发布、checkpoint/恢复与清理，实际规模如实记录；GRPO/PPO 均达到预登记健康阈值，报告训推 logprob 偏差、裁剪比例、奖励分布，无发散；GRPO 在预登记留出评测上给出学习提升证据（门槛可低于功能规模），PPO 不要求提升统计；在实际布局上验证 router replay；同时复核 AC-10、16、17、18、19、20、22、26 的目标范围 | 目标生产运行 |
| AC-29 | 模块导入边界成立；新增任务、recipe 或策略有独立例子；真实路径使用实际后端和 Odyssey 控制循环 | 代码检查 + 集成 |
| AC-30 | 功能验收模型上 GRPO 与 PPO 分别取得学习提升：独立评测提升的置信区间下界超过预登记阈值，或在同一数据与预算下与已证明有提升的参考实现学习曲线一致到登记容差内（容差不能容许无提升曲线通过）；随曲线报告训推 logprob 偏差、裁剪比例和奖励分布 | 真实训练 + 独立评测 |

“至少两次更新”只是 smoke 的最低条件。时间压缩的工具替身可用于状态机测试，但 AC-23 的长程证据需要实际 workload。

## 7 设计依据

- [PPO](https://arxiv.org/abs/1707.06347)、[GAE](https://arxiv.org/abs/1506.02438)、[DeepSeekMath GRPO](https://arxiv.org/abs/2402.03300)：基础算法。
- [Dr. GRPO](https://arxiv.org/abs/2503.20783)、[DAPO](https://arxiv.org/abs/2503.14476)：按样本求均值的长度偏置，本项目采用 token 级归一化。
- [QwenGyre](https://arxiv.org/abs/2609.33848)：长程 Agent 的 rollout/训练弹性 GPU 切换，最接近的已有工作。
- [slime fully async](https://github.com/THUDM/slime/blob/18868a79b0b083a093798a94ed0f8cb4f71b9c14/slime/rollout/fully_async_rollout.py)、[verl V1 async](https://verl.readthedocs.io/en/latest/advance/v1_async_trainer.html)：超发、接续、异步候选和版本处置的工程参照。
